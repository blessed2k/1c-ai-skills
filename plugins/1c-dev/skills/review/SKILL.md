# Ревью (1С)

Два режима:

| Режим | Когда | Что проверяем | Оси |
|---|---|---|---|
| **Шаг** | после каждого шага `step`; «сделай ревью», «ревью с коммита X» | изменение шага или то, что назвали | «Стандарты», «Спека шага» |
| **Задача** | после последнего шага агента в `step`; «итоговое ревью», «ревью задачи» | всё изменение задачи | «Спека целиком», «Пользователь» |

«Проверь глазами пользователя» это режим задачи с одной осью «Пользователь».

Каждая ось идёт в своём суб-агенте, оси режима **запускаются параллельно**, чтобы одна ось не
засоряла контекст другой. Задание каждой оси лежит отдельным файлом в папке `references/` рядом с
этим скиллом. Ты собираешь отчёты. Ревью ничего не правит, только докладывает.

Стандарты в режиме задачи не проверяются: это сделало ревью каждого шага. Если задачу делали без
`step` и ревью шагов не было, добавь к режиму задачи ось «Стандарты» на всё изменение.

## 1. Режим

1. **Вызов из `/1c-dev:step`**: режим называет `step`.
2. **Слова пользователя**: «итоговое», «ревью задачи», «вся задача», «приёмка» дают режим задачи;
   «глазами пользователя» даёт режим задачи с одной осью «Пользователь».
3. Иначе режим шага.

## 2. Что проверяем

**Режим шага.** Возьми первое подходящее:

1. **Вызов из `step`**: изменение этого шага. В режиме `files` это правки в файлах: при git
   `git diff HEAD` и новые неотслеживаемые файлы шага, без git список изменённых файлов. В режиме
   `listing` это готовый листинг с адресом вставки: передай его суб-агентам текстом.
2. **Аргумент**: коммит, ветка, тег (`git diff <точка>...HEAD`, три точки, и
   `git log <точка>..HEAD --oneline`), путь к файлам или листинг в диалоге.
3. Иначе спроси, что проверять.

**Режим задачи.** Всё изменение с начала задачи:

1. **Точка начала**: коммит или ветка из аргумента, иначе `git merge-base HEAD <основная ветка>`
   (основная: та, на которую указывает `origin/HEAD`, иначе `main` или `master`). Изменение это
   `git diff <точка>` (коммиты задачи и незакоммиченные правки вместе), новые неотслеживаемые
   файлы и `git log <точка>..HEAD --oneline`. Точка совпала с `HEAD` и правок нет: спроси, с какого
   коммита началась задача.
2. **Без git**: файлы, изменённые шагами задачи, по отчётам шагов. В режиме `listing`: листинги
   всех шагов из отчётов или диалога.
3. **Аргумент**: путь к файлам или листинг в диалоге.
4. Не собирается: спроси, что проверять.

До запуска суб-агентов убедись, что ссылка git существует (`git rev-parse <точка>`) и изменение
не пустое. Ошибка должна случиться здесь, а не в суб-агентах.

## 3. Где спека

1. Вызов из `step`: файл спеки и номер шага.
2. Путь из аргумента.
3. Спека в `specs_dir` (из `.claude/1c-dev.md` проекта или `~/.claude/1c-dev.md`, по умолчанию
   `docs/specs`), подходящая по теме или имени ветки.
4. Не нашлась: спроси. Спеки нет: оси «Спека шага» и «Спека целиком» пропускаются с пометкой
   «спеки нет». Ось «Пользователь» работает и без спеки: пользователя она определит сама.

В режиме задачи нужна спека целиком и список шагов с состояниями, а также отчёты шагов, если они
есть в диалоге или в хранилище.

Если в настройках стоит `storage: threadline`, спека и шаги лежат не в файле, а в задаче: возьми
их по скиллу `/1c-dev:threadline` и передай суб-агентам текстом.

## 4. Где стандарты

Нужны только оси «Стандарты».

- Файлы `references/` скилла `bsl-standards`: они лежат рядом с этим скиллом,
  `../bsl-standards/references/`. Передай суб-агенту пути к тем файлам, темы которых задевает
  изменение, по таблице из `bsl-standards/SKILL.md`.
- `../bsl-module-skeleton/SKILL.md`, если изменение добавляет модуль или процедуры.
- Документы проекта о правилах кода: `CLAUDE.md`, `CONTRIBUTING.md`, заметки под фронтматтером
  `.claude/1c-dev.md` и подобное.
- **MCP-сервер v8std**, если он подключён к сессии (инструменты `v8std_*`, сервер
  [v8std.ru](https://v8std.ru), исходники `github.com/zeegin/v8std`). Это полный справочник
  стандартов ИТС, а `bsl-standards` только выборка тем, на которых агент ошибается чаще всего.
  Скажи суб-агенту, локальный ли адрес у сервера (`127.0.0.1` или `localhost`): от этого зависит,
  можно ли отправлять ему код.
- Базовый список запахов лежит в файле оси, `references/axis-standards.md`.

Всё, что уже ловят команды из `checks` (синтаксис, BSL Language Server), суб-агенты не
повторяют.

## 5. Запусти суб-агентов

Все суб-агенты режима одним сообщением. Каждый получает абсолютный путь к файлу своей оси со
словами «прочитай и выполни задание из этого файла» и входные данные ниже. Все только читают,
ничего не правят.

| Ось | Файл | Что передать |
|---|---|---|
| «Стандарты» | `references/axis-standards.md` | изменение (команду diff и коммиты, файлы или листинг), пути к стандартам из пункта 4, есть ли v8std и локальный ли он |
| «Спека шага» | `references/axis-spec.md` | изменение, путь к спеке или её текст, при вызове из `step` номер и текст шага |
| «Спека целиком» | `references/axis-spec-whole.md` | всё изменение задачи, спеку целиком, шаги с состояниями, отчёты шагов, если есть |
| «Пользователь» | `references/axis-user.md` | всё изменение задачи, спеку, `dump_path` из настроек, если задан, и имя базы, если пользователь сказал, что изменение уже в неё установлено |

Без слов пользователя об установке в базу ось «Пользователь» базу не получает и работает по
файлам: что изменение где-то стоит, не предполагай.

Суб-агенты недоступны: пройди оси сам по очереди, читая файл каждой оси, и держи отчёты
раздельными.

## 6. Сведи отчёты

Выведи отчёты под заголовками осей (`## Стандарты`, `## Спека шага`, `## Спека целиком`,
`## Пользователь`), как есть или слегка причесав. **Не смешивай и не переранжируй** находки между
осями.

В режиме задачи блок «Проверить руками» оси «Пользователь» вынеси в самый конец отдельным
заголовком: это список для человека, и он не должен потеряться среди находок.

В конце одна строка: сколько находок по каждой оси и худшая находка *внутри каждой* оси. Одного
победителя на все оси не выбирай: именно от этого защищает разделение.

## Зачем оси раздельно

Изменение может пройти одну ось и провалить другую:

- код по всем стандартам, но делает не то: **стандарты да, спека нет**;
- код делает ровно то, что просили, но нарушает стандарты: **спека да, стандарты нет**;
- каждый шаг сделан по своему тексту, но пункт спеки не попал ни в один шаг: **спека шага да,
  спека целиком нет**;
- всё сделано и чисто, но кнопку видит только администратор, а вместо текста ошибки человек
  получает «непредвиденную ошибку»: **спека да, пользователь нет**.

Отдельные отчёты не дают одной оси скрыть другую. Итоговое ревью идёт один раз на задачу: ревью
шага видит только свой кусок, а то, что видит человек, обычно собирается из нескольких шагов.
