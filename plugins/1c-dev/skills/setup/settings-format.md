# Формат настроек плагина 1c-dev

Этот файл лежит внутри плагина и описывает, как скиллы читают настройки. Создать файл настроек
проще всего командой `/1c-dev:setup`.

## Корень проекта

Все относительные пути в настройках считаются от корня проекта:

1. ближайший вверх от рабочей папки каталог с git-репозиторием;
2. если git нет, ближайший вверх каталог, в котором лежит `.claude/1c-dev.md`;
3. если нет ни того, ни другого, корень не определён.

Когда корень не определён, скиллы ничего не сохраняют по умолчанию, а спрашивают, куда писать.
Так спека не попадёт внутрь чужой выгрузки или случайной папки.

## Где лежат настройки

1. `.claude/1c-dev.md` в корне проекта: настройки этого проекта.
2. `~/.claude/1c-dev.md` в домашнем каталоге: личные настройки для всех проектов.

Поля объединяются по одному: значение из проекта главнее, недостающее берётся из личного файла,
а чего нет нигде, берётся из умолчаний ниже. Если нет ни одного файла, скиллы работают на
умолчаниях и один раз предлагают запустить `/1c-dev:setup`.

Обычная раскладка:

- в личном файле то, что одинаково во всех проектах: `author_marker`, `executors`, `mcp`, а также
  `checks`, если в командах пути заданы через подстановки;
- в файле проекта то, что зависит от проекта: `dump_path`, `specs_dir`, `edit_mode`, `checks` с
  особыми путями.

Если в одной папке несколько проектов (несколько репозиториев с выгрузками), общие поля идут в
личный файл, а `dump_path` и `checks` в файл того проекта, с которым сейчас работаете.

## Формат

Markdown-файл с YAML-фронтматтером. Ключи плоские, у `checks` значение списком. Всё, что ниже
фронтматтера, скиллы читают как свободные заметки о проекте.

| Поле | Значения | По умолчанию | Кто читает |
|---|---|---|---|
| `edit_mode` | `listing`: агент готовит листинг, человек вставляет его в конфигуратор. `files`: агент сам правит XML-выгрузку или проект EDT под git | `listing` | step |
| `author_marker` | Шаблон маркера вокруг сгенерированного кода, `{date}` заменяется датой ДД.ММ.ГГГГ. `none`: без маркеров | `none` | step |
| `specs_dir` | Папка для спек и списков шагов: относительно корня проекта или абсолютный путь | `docs/specs` | spec, tickets, step |
| `checks` | Список команд проверки после правки: синтаксис, YAxUnit, Vanessa, свой скрипт. Поддерживает подстановки, см. ниже | пусто: шаг закрывается с пометкой «не проверено» | step |
| `dump_path` | Папка XML-выгрузки конфигурации (где лежит `Configuration.xml`), относительно корня проекта или абсолютный путь | не задан: скилл ищет выгрузку в проекте, не нашёл, спрашивает | grill, spec, step |
| `mcp` | Имя MCP-сервера для 1С, если он подключён. `none`: работать только по выгрузке | `none` | grill, spec |
| `executors` | Кто выполняет шаги, через запятую. Для своего исполнителя можно указать скилл передачи: `джун -> /brief` | `агент, человек` | tickets, step |

### Подстановки в `checks`

Перед запуском команды `step` заменяет:

- `{dump_path}` на абсолютный путь к выгрузке;
- `{project_root}` на абсолютный путь к корню проекта.

Поэтому одну команду можно держать в личном файле для всех проектов:
`vrunner syntax-check --src-path {dump_path}`. Если подстановка не определена (например, не задан
`dump_path` и выгрузка не нашлась), команда не запускается, и шаг помечается «не проверено» с
причиной.

### Ограничения

- `edit_mode` принимает только `listing` или `files`. В режиме `listing` агент не трогает файлы
  конфигурации, а в режиме `files` ничего не загружает в базу: загрузка и обновление базы всегда
  остаются за человеком.
- Маркеры авторства ставятся только в код на встроенном языке, не в XML ролей, форм и схем.
- В файл не пишутся пароли, токены и строки подключения. Если команде проверки нужен пароль,
  передавайте его через переменную окружения.

## Пример

```markdown
---
edit_mode: files
author_marker: "//Иванов И.И. {date}++ ... //Иванов И.И. {date}--"
specs_dir: docs/specs
checks:
  - vrunner syntax-check --src-path {dump_path}
  - vrunner xunit tests --src-path {dump_path}
dump_path: src/cf
mcp: none
executors: агент, человек, джун -> /brief
---

База разработки: файловая, лежит вне репозитория. Типовая конфигурация на БСП 3.1.
Доработки ведём расширением, заимствования только через &После, если есть точка расширения БСП.
```
