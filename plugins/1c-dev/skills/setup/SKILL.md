# Настройка 1c-dev

Собираешь файл настроек, который читают остальные скиллы плагина. Формат, умолчания, правило
корня проекта и подстановки описаны в файле `settings-format.md` рядом с этим скиллом: прочитай
его перед работой. Здесь порядок действий.

## 1. Что уже есть

Прочитай оба файла, если они существуют: `.claude/1c-dev.md` в корне проекта и
`~/.claude/1c-dev.md`. Покажи, что уже задано и откуда. Существующий файл не перезаписывай
целиком: правишь только поля, которые человек решил поменять, заметки под фронтматтером
сохраняешь.

## 2. Факты собери сам

Не спрашивай то, что можно выяснить:

- **Корень проекта.** По правилу из `settings-format.md`: git-репозиторий или папка с
  `.claude/1c-dev.md`. Корня нет: скажи об этом, файл проекта писать некуда, пока его не выберут.
- **Выгрузки.** Найди `Configuration.xml` в рабочей папке (без захода в `node_modules`, `.git` и
  каталоги сборки). Для каждой выгрузки запомни путь и репозиторий, в котором она лежит.
  Нашлась одна: это кандидат для `dump_path`.
- **Несколько проектов.** Если выгрузки лежат в разных репозиториях, рабочая папка это не один
  проект, а несколько. Перечисли их: путь выгрузки и корень репозитория у каждого.
- **Git.** Лежит ли выгрузка под git. Это подсказка для `edit_mode`.
- **MCP.** Какие MCP-серверы подключены в сессии и есть ли среди них сервер для 1С. Это кандидат
  для `mcp`.
- **Проверки.** Есть ли в проекте `vrunner`, `packagedef`, конфигурация YAxUnit или Vanessa,
  свои скрипты проверки. Это кандидаты для `checks`.

## 3. Спроси решения

Сначала спроси, куда писать:

- **один проект**: в проект (`.claude/1c-dev.md` в его корне, для всей команды) или в личный файл
  (`~/.claude/1c-dev.md`, для всех ваших проектов);
- **несколько проектов**: рекомендуй общие поля (`author_marker`, `executors`, `mcp`, `checks` с
  подстановками) в личный файл, а `dump_path`, `specs_dir`, `edit_mode` и `checks` с особыми путями
  в файл конкретного проекта. Спроси, в какие проекты писать файл проекта.

Потом задай вопросы по полям одним-двумя раундами. У каждого вопроса дай свой рекомендуемый
ответ с учётом найденных фактов. Если есть инструмент вопросов с вариантами, используй его.

1. `edit_mode`: `listing` (агент готовит листинг, вставляете вы в конфигуратор) или `files`
   (агент правит выгрузку или проект EDT под git). Рекомендуй `files`, только если выгрузка
   лежит под git.
2. `author_marker`: нужны ли маркеры авторства и в каком виде. Шаблон с `{date}`, например
   `//Иванов И.И. {date}++ ... //Иванов И.И. {date}--`, или `none`.
3. `specs_dir`: куда класть спеки и списки шагов. По умолчанию `docs/specs`.
4. `checks`: какими командами проверять код после правки. Предложи найденные. Пути к выгрузке
   и проекту в командах пиши через подстановки `{dump_path}` и `{project_root}`: тогда команда
   подходит всем проектам и её можно держать в личном файле.
5. `dump_path`: путь к выгрузке. Предложи найденный.
6. `mcp`: имя MCP-сервера для 1С или `none`.
7. `executors`: кто выполняет шаги. По умолчанию `агент, человек`; свой исполнитель можно
   связать со скиллом передачи: `джун -> /brief`.

Поля, которые человек пропустил, в файл не пиши: для них сработают умолчания.

## 4. Запиши и проверь

- Покажи каждый итоговый файл целиком и дождись подтверждения.
- Запиши его. Каталог `.claude` создай, если его нет.
- Проверь сам: фронтматтер открывается и закрывается `---`, ключи только из списка выше,
  `edit_mode` равен `listing` или `files`, `checks` оформлен списком.
- Файл проекта предложи закоммитить: он нужен всей команде. Личный файл в репозиторий не кладётся.

## Правила

- Пароли, токены и строки подключения в файл не записываются. Если команде проверки нужен пароль,
  укажи в ней переменную окружения.
- Настройка ничего не делает с базой 1С: не запускает, не выгружает и не обновляет.
- В конце назови следующий шаг: `/1c-dev:grill`, чтобы разобрать первую задачу.
