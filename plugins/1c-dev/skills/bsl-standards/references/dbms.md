# PostgreSQL и MS SQL

Один и тот же запрос 1С на разных СУБД получает разный план и по-разному блокирует данные.
Источники: документация платформы (приложение «Особенности работы с различными СУБД», глава
«Работа с данными»), стандарты #std435, #std412, #std729, #std663, #std664 и методические
статьи раздела «Технологические вопросы крупных внедрений» на ИТС.

Сначала узнай СУБД целевой базы. Если она неизвестна, пиши запрос так, чтобы он был приемлем
на PostgreSQL: там ограничений больше.

## Что меняется в тексте запроса

| Тема | PostgreSQL | MS SQL |
|---|---|---|
| Сложный запрос (много таблиц, подзапросы) | плохой план вероятнее, упрощай и дели на временные таблицы | терпимее, правило то же |
| `ПОЛНОЕ СОЕДИНЕНИЕ` | медленно; с табличной частью в выборке запрещено | работает |
| `Поле = &А ИЛИ Поле = &Б` | заменяй на `Поле В (&А, &Б)`: с 8.3.22 эта форма выполняется быстрее цепочки `ИЛИ` | без разницы |
| Сортировка по полю с `NULL` | по возрастанию `NULL` последние, по убыванию первые | порядок другой; оборачивай поле в `ЕСТЬNULL` |
| `[...]` в шаблоне `ПОДОБНО` | работает только в литерале, в выражении нет | не используй: #std726 |
| Первый индекс временной таблицы | обычный | кластерный |
| Массовое удаление и вставка | производительность падает, нужны `VACUUM` и `REINDEX` | нужны регламентное обновление статистик и дефрагментация индексов |
| Длина записи индекса | в документации платформы не названа | не больше 900 байт, ошибка возникает при вставке |

С версии 8.3.21 оператор `(А, Б) В (ВЫБРАТЬ ...)` на PostgreSQL выполняется через `EXISTS` и
всегда возвращает булево. В режиме совместимости 8.3.20 и ниже поведение прежнее.

## Блокировки

| Режим блокировок | PostgreSQL | MS SQL |
|---|---|---|
| Автоматический: что блокируется | **таблица целиком** | записи |
| Автоматический: чтение вне транзакции | согласованное | «грязное» |
| Управляемый: уровень изоляции | Read Committed | Read Committed Snapshot |
| Управляемый: что блокируется | записи | записи |

- Конфигурация в автоматическом режиме на PostgreSQL блокирует таблицы целиком. Для работы
  нескольких пользователей нужен управляемый режим.
- Разделение итогов регистра на PostgreSQL в автоматическом режиме не работает.
- В управляемом режиме на PostgreSQL ожидания должны возникать только на управляемых
  блокировках 1С. Ожидание на блокировке самой СУБД считается ошибкой: фиксируй сценарий.
- На MS SQL длительная транзакция раздувает `tempdb`: версии строк хранятся там до её конца.

## Как получить настоящий план запроса

Без плана вывод о скорости запроса остаётся предположением. Назови это прямо, если доступа к
стенду нет.

**PostgreSQL.** Платформа выполняет запросы со своими параметрами соединения. План, снятый без
них, не совпадает с тем, что получает 1С.

1. Взять текст SQL из события `DBPOSTGRS` технологического журнала.
2. Перед запросом задать параметры соединения платформы:

```sql
SET enable_mergejoin = off;
SET cpu_operator_cost = 0.001;
SET lock_timeout = 20000;
```

3. Если запрос читает временные таблицы, воссоздать их: создание таблицы, индекс, вставка
   данных, `ANALYZE` по каждой. Запросы заполнения лежат в журнале выше исследуемого.
4. Выполнить `EXPLAIN ANALYZE VERBOSE` на копии базы или тестовом стенде.

Таблица значений, переданная в запрос параметром, загружается во временную таблицу мимо
журнала. Для таких запросов план берут модулем `auto_explain` с порогом по длительности.
Сбор планов в технологический журнал на рабочем сервере не включают.

Быстрая оценка по журналу: если суммарная длительность событий `DBPOSTGRS` больше примерно
половины суммарной длительности `CALL`, время уходит на запросы.

**MS SQL.** Текст берут из события `DBMSSQL`, план смотрят средствами самой СУБД на копии
базы. Узкое место сервера ищут по типам ожиданий:

| Ожидание | Что значит |
|---|---|
| `CXPACKET` | параллельное выполнение запроса; для 1С ставят `max degree of parallelism = 1` |
| `PAGEIOLATCH_*` | медленный диск с файлами данных |
| `WRITELOG` | медленный диск с журналом транзакций |
| `LATCH_*` | внутренние защёлки сервера СУБД |

Устаревшая статистика на MS SQL даёт плохие планы: её обновляют регламентно, не реже раза в
день.

## Управляемые блокировки в журнале

События технологического журнала для разбора ожиданий: `TLOCK` (установка управляемой
блокировки, в свойствах время ожидания), `TTIMEOUT` (истекло время ожидания), `TDEADLOCK`
(взаимоблокировка).
